# 在新电脑安全接手

## 第一步：只核验，不启动项目

把整个交接包复制到新目录。在交接包根目录运行校验脚本，再用 Git 查看源码 HEAD、差异和 fsck。具体命令见根 README。

本包的仓库目录是 `source/Kronos-Decision/`，并非交接包根目录。进入源码后才可使用计划中的 `decision/`、`tests/` 等相对路径。

## 第二步：记录新机器条件

由 PRE0 读取实际 OS、Python/Conda、Git、CPU/GPU、显存/内存、磁盘、网络与目录权限。不要把本机或历史电脑的情况当作新机器状态。

校验脚本只需 Python 标准库；它不导入项目，也不会下载权重。项目运行还需要哪些依赖，必须依据实际 requirements 与源码核验。当前根 requirements 和 Web requirements 约束并不完全一致，尚未完成统一和锁定。

## 第三步：处理旧入口，而不是盲目照旧 README 启动

审查基线的 `start.bat` 硬编码旧机器的 `D:\miniconda3\envs\kronos\python.exe` 和 `C:\Users\xzh\Desktop\kronos`，并有缺依赖自动安装行为。这些路径保留在原始源码中用于修复，不适用于新电脑。

旧 `webui/run.py` 有 debug/全部网卡监听问题；数据路径、模型设备、配置持久化和测试隔离也未完成重构。不要为验证迁移而直接运行它。M0 按计划修复后才验收安全启动。

## 第四步：从隔离环境开始实施

只有用户授权后才准备项目环境或安装依赖。可以保留 Conda 工作习惯，但环境名称、Python 版本、PyTorch/CUDA 组合需由新机验证，不搬旧虚拟环境目录，不修改全局 PATH 来适配旧脚本。

优先离线契约与隔离测试；真实数据源和模型推理按任务单独授权、单独记证据。Qlib 的依赖例外 D01 尚未批准。

## 数据位置与备份边界

原代码的配置入口为仓库内 `decision/config.yaml`；默认行情缓存字符串是 `data/cache`，日志配置含 `logs/kronos.log`。这些是读取到的旧默认值，不是新版本统一数据目录已经实现。必须检查消费者和实际工作目录后再操作。

本包不迁移任何个人运行数据库、持仓或已下载模型。如另有旧运行数据，先明确源目录、数据用途、版本和备份；不要将运行中的 SQLite 主库、WAL/SHM 当普通独立文件分别拷贝。

## 常见问题

- **校验失败：** 先检查是否复制遗漏或已开始修改，保留现场，不运行未知代码；从原包重新复制到新目录，不覆盖已有用户改动。
- **源码不是最新：** 固定旧基线是有意行为。先比较新提交影响，再更新任务输入；不要一上来 git pull 抹掉评估依据。
- **没有网络：** 文档、源码和 Git 历史可以离线阅读/恢复；依赖、市场数据、权重并未随包提供，真实实验可能阻塞。
- **新电脑没有 Hermes 技能：** 直接读取 `rules/enough/` 与计划即可接手规则，不声称工具或模型已安装。子代理工具不可用时说明限制，不伪造并行执行。
- **没有新项目环境：** 这是正常的待实施状态。先做只读 PRE0，不把环境缺失当作已实现功能的代码缺陷。
